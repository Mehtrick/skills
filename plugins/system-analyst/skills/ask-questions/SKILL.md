# Clarify a requirement

Interview the user about the requirement they provide. Use the project's documentation language, or the user's language when there is no project convention. If the requirement is missing, ask the user to describe it.

For repository work, follow the [shared architecture index workflow](../analyze-requirements/references/architecture-index.md) to find relevant requirements, use cases, glossary entries, code, and tests. Use available evidence to answer factual questions and distinguish existing behavior from the requested change. Cite relevant sources when they inform a question or expose a conflict.

Ask only about uncertainties that affect the requirement or its observable outcome. Identify the actor, goal, trigger, business rules, outcomes, and relevant alternatives as needed. Explore permissions, state changes, boundaries, and failure cases when they matter. Challenge ambiguous terms and assumptions with concrete examples.

Ask in short, numbered rounds. Group independent questions that can be answered now, and leave questions that depend on an answer for a later round. Explain the decision each question affects and offer a recommendation with its trade-off when the evidence supports one. Wait for the user's answers, incorporate them, and continue with the remaining material questions. If the user requests an explanation or an example, provide it and resume the open question.

When the requirement is clear enough for the user's goal, summarize the agreed behavior, testable outcomes, and any deferred decisions. If asked to create or revise a use case, hand the confirmed answers and relevant evidence to [write-use-case](../write-use-case/SKILL.md). Follow the user's requested scope for any documentation or implementation changes.
